# Web アプリ立ち上げ（プロトタイプ / バックエンド込み）

社内向け Web アプリを、目的に合った最小構成で立ち上げるためのスキル。
新規開発では仕様を聞くのと同時に、次のどちらで進めるかをユーザーと確定する。

| 開発モード | 目的 | 構成 | 動作確認 |
|---|---|---|---|
| **フロントエンドプロトタイプ** | 画面・導線・入力項目を早く検証する | Sites 上で動くフロントエンド。サンプルデータまたは端末内だけの状態 | Sites に公開して URL を渡す |
| **バックエンド込み** | 共有データ、認証、権限、監査を含む運用を始める | Vue 3 + Vuetify / FastAPI / 1 コンテナ | ローカル確認後、Cloud Run・k3s・GCE などへ公開 |

**新規開発で開発モードを推測だけで確定しない。** ユーザーが明示済みなら復唱し、
明示されていなければ Q1・Q2 とまとめて短く確認する。判断基準と Sites での進め方は
`references/prototype.md` を読む。

## バックエンド込み構成を選ぶ理由

社内ツールは「作った人以外が運用する」「利用者は非エンジニア」「対象は数十〜数百人」という
条件になりやすい。そこで次の判断を既定にしている。理由が当てはまらない案件では変えてよい。

| 判断 | 理由 |
|---|---|
| フロントとバックエンドを 1 リポジトリ・1 コンテナに同梱 | デプロイ対象が 1 つで済み、CORS もほぼ不要。少人数運用で壊れにくい |
| SPA を FastAPI 自身が配信（別 CDN を使わない） | 認証を挟むのが簡単。未ログインは `/login` に飛ばすだけで守れる |
| セッション Cookie 認証（JWT をフロントに持たせない） | XSS でトークンを抜かれる経路を減らせる。SPA 側に認証ロジックを持たない |
| 状態は JSON/JSONL ファイル + マウントしたボリューム | 小規模ならこれで十分。DB 運用の手間を後回しにできる。規模が読めたら移行する |
| Vuetify を採用 | 非エンジニアが使う画面で、デザインを詰めずに一定品質を出せる |

**判断が変わる境界を先に伝えること。** 同時書き込みが増える／履歴を検索したい／複数インスタンスに
スケールする、のいずれかが見えた時点で、ファイル保存は Firestore や Cloud SQL に移す。
最初からその予定があるならユーザーに確認してから構成を変える。

ただし**「ファイル保存のまま公開したい」だけなら、DB に移す前に選択肢がある。**
GCE の VM 1 台（Container-Optimized OS）＋ 永続ディスクにすれば、
Cloud Run の複数インスタンス問題を避けたまま HTTPS 公開できる。
常時起動・固定 IP・コールドスタート無しが要るときも同じ。→ `gce-cos-deploy`

## 進め方

### 開始条件：ヒアリング → 仕様案の合意 → プロジェクト作成 → 実装

新規開発の既定は対話型ヒアリング。まず `references/intake.md` を読み、どんなアプリにするかを
ユーザーと具体化する。目的、利用者、主要操作、入力項目、画面、開発モード、保存方法、公開範囲を
会話で整理し、仕様案を提示して「この内容で作成を始めてよいか」の返答を待つ。
質問は一度に 2〜3 件程度にまとめ、回答済みの内容は聞き直さない。
**選択式の質問ツールが利用可能なら、ヒアリングで必ず実際に呼び出す。**
Codex の通常モードでは `request_user_input_async` を使う。ツール名を書いた説明や
Markdown の選択肢一覧だけでは質問UIは表示されない。質問文だけを文章で列挙せず、
短い選択肢と「選ぶとどうなるか」の説明を付ける。IT 用語を選択の前提にしない。
質問UIの使い分けと例は `references/intake.md` の「答えやすい質問UI」を参照する。
Codex の通常モードで質問UIが使えない場合は、番号付きの文章へ自動的に切り替えず、
`/plan` によるプランモードへの切り替えを案内して、そのターンを終了しユーザー操作を待つ。
切り替え後は実行モードと利用可能なツールを再確認して、未回答の質問から再開する。
詳細は `references/intake.md` の「質問UIが使えない場合」に従う。スキル自体はモードを変更できない。

**合意前にディレクトリ作成、Git 初期化、依存関係のインストール、雛形生成、Sites 登録、
アプリ実装を開始しない。** 提供資料と既存ファイルの読み取り、会話内での仕様案作成は進めてよい。
この開始条件は Sites スキルへ委譲する前に適用する。Sites の「まずセットアップ」は合意後の実装段階で適用する。

「作って」「新規開発」「プロトタイプ」「とりあえず動くものを」だけでは仕様確認の省略を意味しない。
「質問せず任せる」「仕様確認を省略して実装して」などユーザーが明示した場合だけ、
仮定を短く伝えて着手する。すでに具体的な仕様案に合意済みなら再承認は求めない。

### 0. 新規アプリ専用のプロジェクトを作る

新規開発の依頼では、アプリのソースを編集する前に専用プロジェクトを作る。
現在開いているリポジトリが別用途なら、その中へアプリを直接追加しない。
詳細は `references/project-setup.md` を読む。

先に下記のヒアリングを会話内で行い、仕様案への合意後にアプリ名・開発モード・配置先に従って作成する。

- **フロントエンドプロトタイプ** — `sites:sites-building` の新規セットアップを最初の実作業にし、
  専用のローカルプロジェクトと Sites プロジェクトを作る
- **バックエンド込み** — `<app-name>/` を専用プロジェクトルートとして作り、原則 Git を初期化してから
  `docs/app-spec.md` と雛形を配置する。GCP など外部のクラウドプロジェクトは自動作成しない

同名ディレクトリが既にあり空でない場合は上書きせず、既存アプリか名前の衝突かを確認する。
ユーザーが既存プロジェクトへの追加を明示した場合は新規作成せず、そのプロジェクトを使う。

### 1. ヒアリングして仕様書にする

**プロジェクト作成前に聞き、会話内で仕様案への合意を得る。**
合意後、作成したプロジェクトの `docs/app-spec.md` に保存し、以降の実装はそこを見て進める。

最初に開発モードを確認し、その後 6 グループを必要な範囲で聞く。
手順と質問の言い回しは `references/intake.md` にある。

| | 聞くこと | ここから決まるもの |
|---|---|---|
| Q0 | **開発モード** — まず画面を試すか、共有データを扱う運用版まで作るか | フロントエンドプロトタイプ / バックエンド込み |
| Q1 | **何を管理するアプリか** — 誰が・何を・何のために（一文） | アプリ名、画面タイトル |
| Q2 | **記録する情報** — 1 件登録するときの入力項目 | エンティティと項目の型。**ここが本体** |
| Q3 | **一覧の見せ方** — 何の一覧が出ていてほしいか、そこから何を探すか | 一覧の列、絞り込み、詳細画面の要否 |
| Q4 | **マスタ** — 運用しながら増える選択肢はあるか | マスタか enum かの切り分け |
| Q5 | **権限** — できることで分けると何種類か | 機能キー |
| Q6 | **運用** — 人数、件数、社外から使うか | 保存方式、デプロイ先 |

**Q2 は現物を送ってもらうのがいちばん速い。**
言葉で聞き出すより、読むほうが速くて正確で、相手も「説明する」負担が無い。
形式は指定しない。**Excel でも、画面のスクリーンショットでも、紙を撮った写真でも、
PDF の様式でも読める。** 相手が出しやすいものを出してもらう。
「今はどうやっていますか」と聞くと、たいてい現物が出てくる。

ただし**資料から確定できるものと、必ず聞くものは分かれる。**

- 確定できる — 項目名と並び、入力部品の種類、実データからの型、件数
- **必ず聞く** — **enum の全候補**（プルダウンは閉じた状態で写る）、
  **必須かどうか**（Excel の空欄は任意とは限らない）、
  **紙にしか要らない項目**（押印欄・控え番号は、システム化で不要か確認する）

読み取ったら**そのまま項目表にして見せ、確認を取ってから進める。**
不明な点は空欄にせず、推測を入れて `❓` を付ける。空欄だと相手は何を答えればよいか分からない。

「とりあえず動くものを」と言われたらプロトタイプを提案し、対象業務と中心となる操作を聞いて
仕様案にまとめる。省略する機能や仮定も着手前に提示する。プロトタイプでは権限や永続化を
実装済みのように見せかけず、未実装の制約を仕様書と最終報告に明記する。

雛形は `assets/app-spec.template.md` をコピーする。

```bash
mkdir -p docs && cp "$SKILL_DIR/assets/app-spec.template.md" docs/app-spec.md
```

**仕様書の書き方を自由記述にしないこと。** 項目の型を 11 種類の語彙に固定してあるので、
表がそのまま `types.ts` の interface とフォームの部品に写る。
どの節がどのファイルになるかの対応表も `references/intake.md` にある。

バックエンド込みでは、**作る順番は「1 エンティティを縦に通す」。**
domain → api → types → composable → 画面まで 1 つ通して見せ、
形が合っているか確認してから 2 つ目に進む。プロトタイプでは、主要画面と代表データ、
中心となる操作を先に Sites で触れる状態にする。

### 2. 開発モードに沿って実装する

#### フロントエンドプロトタイプ

`references/prototype.md` を読み、`sites:sites-building` に従って実装する。
バックエンド、実認証、サーバー側権限判定、共有永続化は作らない。
ブラウザ保存を使うのは、端末内だけの状態であることをユーザーが受け入れた場合に限る。

ビルドに成功したら `sites:sites-hosting` に従って Sites へ公開し、動作確認 URL を渡す。
公開範囲は Sites の既存アクセス設定と承認ルールに従い、勝手に公開範囲を広げない。

#### バックエンド込み

以下の雛形を配置する。

`assets/` の中身をプロジェクト直下にコピーし、プレースホルダを置換する。

```bash
SKILL_DIR="${APP_FORGE_SKILLS:-${CODEX_HOME:-$HOME/.codex}/skills}/webapp-scaffold"
cp "$SKILL_DIR/assets/Dockerfile" "$SKILL_DIR/assets/Makefile" \
   "$SKILL_DIR/assets/cloudbuild.yaml" "$SKILL_DIR/assets/env.yaml" \
   "$SKILL_DIR/assets/.dockerignore" ./
cp "$SKILL_DIR/assets/gitignore" ./.gitignore
```

置換するプレースホルダ（すべてのファイル共通）:

| プレースホルダ | 例 |
|---|---|
| `__APP_NAME__` | `factory-management-agent` |
| `__APP_TITLE__` | `工場管理支援エージェント` |
| `__GCP_PROJECT__` | `my-project-123456` |
| `__GCP_REGION__` | `asia-northeast1` |

次に、フロントとバックエンドをそれぞれのスキルで作る。

- フロント → `vue-vuetify-frontend` スキルを読む
- バックエンド → `fastapi-backend` スキルを読む
- ログイン・権限・監査ログ → `webapp-auth-security` スキルを読む
- GCE の VM 1 台で常時起動・HTTPS 公開 → `gce-cos-deploy` スキルを読む

### 3. バックエンド込みのディレクトリ構成

```
<app-name>/
├── Dockerfile              # フロント→バックエンドの多段ビルド
├── Makefile                # ローカル/社内レジストリ向け build & push
├── cloudbuild.yaml         # Cloud Build → Cloud Run
├── env.yaml                # Cloud Run に渡す環境変数（秘密は入れない）
├── .dockerignore
├── README.md               # 起動手順・環境変数・運用手順
├── docs/app-spec.md        # ヒアリングの結果。実装はここを見て進める
├── backend/
│   ├── main.py             # FastAPI エントリポイント。ルータ登録と SPA フォールバック
│   ├── requirements.txt
│   ├── .env.sample         # .env は必ず gitignore する
│   ├── config/settings.py  # 環境変数を 1 クラスに集約
│   ├── core/               # 認証・セキュリティヘッダー・共通ヘルパ・監査ログ
│   ├── api/                # HTTP ルータ。1 機能 1 ファイル
│   ├── domain/             # 業務ロジック。FastAPI に依存させない
│   ├── data/               # 永続データ（gitignore、本番はボリュームマウント）
│   ├── templates/login.html
│   └── tests/
└── frontend/
    ├── package.json
    ├── vite.config.ts      # /api などを backend にプロキシ
    ├── tsconfig.json
    └── src/
        ├── main.ts         # トークン読み込み・Vuetify テーマと defaults・ルータ
        ├── App.vue
        ├── styles/         # tokens.css（色・文字・余白）と base.css（共通部品）
        ├── types.ts        # バックエンドのレスポンス型を集約
        ├── composables/    # 状態と API 呼び出し
        ├── components/
        └── views/
```

`domain/` を `api/` から分けているのは、業務ロジックをテストしやすくするため。
`api/` は「入力を検証して domain を呼び、結果を JSON にする」だけに留めると、
テストが FastAPI の TestClient なしで書けて速い。

### 4. バックエンド込みを動かす

開発時はフロントとバックエンドを別々に起動する（Vite の HMR を使うため）。

```bash
cd backend && python main.py
```

`.env` に `APP_ENV=local` を入れておくと、**Google ログインを省いて起動できる。**
OAuth クライアント ID もセッション鍵も未設定でよいので、
認証まわりを後回しにして画面から作れる。
本番で有効にならない仕組みは `webapp-auth-security` にある。

```bash
cd frontend && npm run dev
```

初回は `frontend` で一度 `npm install` を実行して `package-lock.json` を作る。
Dockerfile は `npm ci` を使うので、ロックファイルが無いとイメージのビルドが失敗する。

Vite の dev server が `/api` `/auth` `/login` `/logout` を `http://localhost:8080` に
プロキシするので、Cookie 認証もそのまま動く。
本番相当を確認したいときは `npm run build` してから backend だけ起動する。

Koyorina向けの成果物では、次の3点を完成条件にする。

- `frontend/package.json` の `build` が `vite build` を実行できる
- `frontend/dist` はコミットせず、プレビュー環境でソースから生成する
- バックエンドの `GET /` はSPAの入口または有効なリダイレクトを返し、404にしない

### 5. バックエンド込みをデプロイ

| デプロイ先 | 読むもの | 向いている条件 |
|---|---|---|
| Cloud Run | `references/deployment.md` | 既定。ゼロスケール、運用の手間が最小 |
| 自前 k3s / 社内レジストリ | `references/deployment.md` | オンプレ、プライベート CA 込みの構成 |
| GCE の VM 1 台（COS） | **`gce-cos-deploy` スキル** | ファイル保存のまま公開、常時起動、固定 IP、独自ドメイン HTTPS |

`references/deployment.md` には Cloud Run・自前 k3s・社内レジストリの 3 パターンがある。
GCE は手順もスクリプトも量が多いので、別スキルに切り出してある。

## 全体を通しての約束ごと

`references/conventions.md` に、コメント・命名・エラーメッセージ・環境変数の扱いを
まとめてある。複数人で触るアプリを作るときは一度読むこと。特に効くのは次の 5 つ。

- **利用者に見えるメッセージは日本語、コードは英語。** 利用者は非エンジニアなので、
  エラーは「何が起きたか」ではなく「次に何をすればよいか」を書く。
- **環境変数は `config/settings.py` の 1 クラスに集約する。** `os.getenv` をコードに
  散らすと、必要な設定が把握できなくなり、デプロイ時に必ず事故る。
- **機密は環境変数、しかも Secret Manager 経由。** `env.yaml` に入れてよいのは
  プロジェクト ID やモデル名など、漏れても困らないものだけ。
- **見た目の値は `frontend/src/styles/tokens.css` に集約する。** 色・文字サイズ・余白を
  コンポーネントに直接書くと、画面が増えるほど不揃いが積み上がり、
  直すときは全画面の修正になる。詳細は `vue-vuetify-frontend`。
- **セキュリティヘッダーは最初から入れる。** `backend/core/security_headers.py` を
  `main.py` のいちばん先に登録する。後付けにすると、動いている画面が CSP で
  まとめて壊れ、原因の切り分けに時間を取られる。詳細は `fastapi-backend`。
