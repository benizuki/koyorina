# 新規アプリのプロジェクト作成

新規開発では、既存のスキルリポジトリや無関係なアプリへコードを混在させない。
会話内で仕様案への合意を得てから、アプリごとに専用のプロジェクトルートを作って実装する。

## 新規作成か既存利用か

- 「新しいアプリを作る」は新規プロジェクトを作る
- 「このアプリに追加する」「このリポジトリを直す」は指定された既存プロジェクトを使う
- 判断できない場合は、現在のプロジェクトを変更してよいと推測せず、新規アプリか既存改修かだけ確認する

## 作成前に確定する最小情報

依頼文から次を決める。分からないものだけを一度に短く確認する。

- アプリ名: 英小文字のケバブケース。プロジェクトディレクトリ名にも使う
- 画面タイトル: 日本語の利用者向け名称
- 開発モード: `frontend-prototype` または `backend-included`
- 配置先: ユーザー指定の親ディレクトリ、または新規作成が許された空の作業領域

この情報だけでは着手しない。`intake.md` に従って画面・操作・項目を含む仕様案を提示し、
ユーザーが作成開始に合意した後にプロジェクトを作る。明示的な確認省略依頼は SKILL.md の開始条件に従う。

## 共通の安全条件

- 既存の空でないディレクトリへ初期化処理を重ねない
- 現在のリポジトリがスキル、ライブラリ、別アプリなら、その直下を新アプリのルートにしない
- ユーザーの既存ファイル、Git 設定、履歴を上書きしない
- 新規プロジェクトのルートを決めた後は、仕様書、ソース、ビルド成果物をその中に閉じる
- 外部 GitHub リポジトリ、GCP プロジェクト、課金リソースは、依頼や必要な承認なしに作らない

## フロントエンドプロトタイプ

仕様案への合意後に `sites:sites-building` を読み、実装段階の最初の作業として新規セットアップを使う。
独自の初期化コマンドで代用したり、生成済みプロジェクトへ二重に initializer を実行したりしない。

ホストする新規 Site では、生成された `.openai/hosting.json` を確認し、`project_id` が無ければ
`sites:sites-building` の手順で Sites プロジェクトを一度だけ作成して記録する。
登録時点では非公開であり、完成・ビルド成功後の公開は `sites:sites-hosting` に従う。

## バックエンド込み

専用の `<app-name>/` ディレクトリを作り、そのディレクトリをプロジェクトルートにする。
ユーザーが禁止していなければローカル Git リポジトリを初期化し、最初から秘密情報と生成データを
追跡対象外にする。その後に `docs/app-spec.md` とバックエンド込みの雛形を配置する。

ローカルプロジェクトの作成と、Cloud Run などの公開先作成は別の操作である。
実装開始のためだけに GCP プロジェクト、Artifact Registry、VM、ロードバランサを作らない。

## 作成後の進行

プロジェクトルート内に `docs/app-spec.md` を作り、合意済みの仕様案を記録する。
作成後の進捗報告では、プロジェクト名、開発モード、最初に実装する機能を伝える。
最終報告ではプロジェクトルートを示し、Sites へ公開した場合は動作確認 URL も渡す。
