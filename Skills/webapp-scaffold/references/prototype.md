# フロントエンドプロトタイプと開発モードの選択

新規開発では、仕様確認と同時に「フロントエンドプロトタイプ」か
「バックエンド込み」かをユーザーと確定する。技術構成を先に押し付けず、
何を検証したいかと、実データを扱う必要があるかで選ぶ。

## 確認のしかた

Q1（目的）と Q2（記録する情報）のヒアリングで、次の意味が伝わる一問を聞く。

`intake.md` の「答えやすい質問UI」に従い、「今回はどこまで作りますか？」を
説明付きの選択肢（まず画面を試す / 実際の業務で使う / 画面確認後に業務用へ進む）で聞く。

ユーザーが判断しやすいよう、要件から推奨案と理由を一緒に示す。
すでに「プロトタイプ」「本番運用」「バックエンドも必要」などと明示されている場合は
同じ質問を繰り返さず、選択を復唱して仕様書へ記録する。
開発モードの選択だけをアプリ仕様への合意と扱わない。画面・操作・項目を含む仕様案に合意してから
Sites のセットアップへ進む。

## 選択基準

| 要件 | フロントエンドプロトタイプ | バックエンド込み |
|---|---|---|
| 画面、文言、導線、入力項目を試したい | 適する | 過剰になりやすい |
| デモ用サンプルデータでよい | 適する | 不要 |
| 入力を再読み込み後も同じ端末だけで残せればよい | 条件付きで可 | 可 |
| 複数人で同じデータを共有・同時編集する | 不可 | 必須 |
| Google ログイン、実際の権限、サーバー側アクセス制御が要る | 不可 | 必須 |
| 監査ログ、機密情報、秘密鍵を使う外部 API が要る | 不可 | 必須 |
| 通知、定期処理、ファイルの安全な共有保存が要る | 不可 | 必須 |

バックエンド必須の要件が 1 つでもある場合は、その理由を説明してバックエンド込みを推奨する。
ただし、ユーザーが「まず画面だけ」と選ぶなら、該当機能をサンプル表示または非動作の説明に留め、
実装済みと誤認させない。

## プロトタイプの実装境界

- `sites:sites-building` を使い、Sites プロジェクトとして作る。
- 代表的なサンプルデータを同梱し、主要画面、中心操作、空・読込・エラー状態を確認できるようにする。
- 状態を残す必要がなければメモリ内、端末内だけでよければ `localStorage` などのブラウザ保存を使える。
- ブラウザ保存は共有データ、バックアップ、アクセス制御、監査の代わりにしない。
- 実ログインに似せた UI、秘密情報、実顧客データ、実運用 API の資格情報を埋め込まない。
- バックエンド化で置き換えるデータ取得・更新境界を UI コンポーネントから分離しておく。
- プロトタイプのために FastAPI、Docker、Cloud Run、GCE の雛形を配置しない。

## Sites での確認

実装中のプレビューと最終ビルドは `sites:sites-building`、公開は必ず
`sites:sites-hosting` の手順とアクセス承認ルールに従う。
ビルド成功後は Sites に公開し、ユーザーへ URL と次の制約を簡潔に渡す。

- データがサンプルか、再読み込みで消えるか、同じ端末だけに残るか
- ログイン、権限、共有保存など未実装のもの
- 次にバックエンド込みへ進む場合に引き継ぐ画面・項目・操作

## バックエンド込みへ移行するとき

同じ `docs/app-spec.md` を更新し、開発モードを「バックエンド込み」に変更する。
プロトタイプで確定した画面、項目、文言を要件として引き継ぐが、サンプルデータやブラウザ保存を
そのまま本番データ層にしない。`vue-vuetify-frontend`、`fastapi-backend`、
認証・権限・監査が必要なら `webapp-auth-security` を読み、1 エンティティずつ縦に実装する。
