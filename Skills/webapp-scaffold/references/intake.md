# 初期ヒアリングと仕様書

新しいアプリを作る前に、決まった順番で聞き、決まった形の仕様書に落とす。
仕様書は `docs/app-spec.md` に置き、以降の実装はすべてそこを見て進める。
新規アプリでは会話内でヒアリングと仕様案への合意を済ませてから専用プロジェクトを作る。
配置先と初期化の境界は `references/project-setup.md` に従う。

**この手順の目的は「聞き漏らしを無くすこと」ではなく、
「聞いた内容が、どのファイルになるかまで決まっていること」。**
だから仕様書のフォーマットは自由記述にせず、型の語彙まで固定してある。

## 3 つの進め方

相手の答え方で切り替える。**全部を毎回聞かない。**

| モード | いつ | やること |
|---|---|---|
| **標準（既定）** | 新規アプリの開発依頼 | Q0〜Q6 の未確定事項を 2〜3 問ずつ聞き、仕様案を提示して合意を待つ |
| **短縮** | 「質問せず任せる」「仕様確認を省略して実装して」と明示 | 仮定を着手前に伝え、未確定事項を仕様書へ残して進める |
| **追加** | 既存アプリに機能を足す | Q2（新しいエンティティ）と Q5（権限）だけ。既存の `docs/app-spec.md` に追記する |

**対話型ヒアリングを既定とする。** 回答を受けて次の質問を選び、質問だけを大量に並べない。
目的や利用者が不明ならそこから始める。画面や項目は具体案を出して一緒に決める。
「プロトタイプ」「とりあえず」「まかせる」だけでは確認を省かない。

### 答えやすい質問UI

利用可能なネイティブの選択式質問ツールを使い、選択肢をクリックし、必要なら自由入力で補足できる形にする。
一度に 1〜3 問、各質問に 2〜3 個の選択肢を目安とし、回答に応じて次の質問を選ぶ。

- Codex で `request_user_input_async` が利用可能なら、通常モードの仕様ヒアリングに使う。
  `questions[].title` に質問、`options` の各文字列に「短いラベル — 一文の説明」を入れる。
  実際のツール呼び出しが必要。コード例の表示や「UIを表示します」という文章で代用しない。
- `request_user_input` は実行モードとツール説明で利用が許される場合だけ使う。
  `label` と `description` に選択肢名と説明を分ける。通常モードで無理に呼ばない。
- 別の実行環境では、その環境で利用可能な同等の質問ツールを使う。存在しないツールは呼ばない。
- UI が自由入力を提供する場合、「その他」という選択肢を重複して追加しない。
- ツールがない場合は、下記「質問UIが使えない場合」に従う。使えるUIの外見は実行環境に従う。
- 推奨案を先頭に置くのは要件から推奨理由を説明できる場合だけ。常に運用版を推奨しない。
- 初期選択、スキップ、無回答をユーザーの決定として扱わない。非同期の質問中は資料の読み取りと
  仕様案の整理だけを進め、回答が必要な決定やプロジェクト作成は待つ。
  戻り値の `accepted: true` は質問の受付であり、ユーザーの回答や画面表示の確認ではない。
  受付直後に「表示しました」「回答できます」と断定して完了扱いにしない。
  回答が届くまでは同じ質問を再発行せず、利用可能な待機機構でユーザー入力を待つ。
  待機で表示が維持されるかは環境依存であり、消える原因を推測で断定しない。
- 公開などの操作承認は、その操作のツール・実行環境で許可された方法で求める。
  仕様ヒアリングで公開希望を選んだことだけで、別途必要な公開承認を済ませたとは扱わない。

#### 質問UIが使えない場合

1. 現在の実行モード、提供されているツール、その使用条件を確認する。
   `request_user_input` が通常モードで使えないことだけを理由に、利用可能な
   `request_user_input_async` まで使えないと判断しない。失敗した場合は実際のエラーに基づいて説明する。
2. Codex の通常モードで利用できる質問UIがない場合は、次のように案内してターンを終了する。
   質問を番号付きの文章で並べたり、仕様を仮決定して実装へ進んだりしない。

   > このタスクでは、現在のモードで選択式の質問UIを使えません。
   > webapp-scaffold のヒアリング手順に従い、UIで回答できるよう切り替えを待ちます。
   > 入力欄で `/plan` を選び、プランモードに切り替えてから「続けて」と送ってください。

   案内には読み込んだ `SKILL.md` へのリンクと、適用した指示
   「プランモードへの切り替えを案内して、そのターンを終了しユーザー操作を待つ」を添える。
3. 続きのターンで実際のモードを確認する。「続けて」という文章だけをモード変更とは扱わない。
   プランモードで `request_user_input` が利用可能なら呼び出し、回答済みの項目を引き継いで
   未回答の質問から再開する。プランモード中は仕様整理に留め、ファイル作成・実装は行わない。
   仕様合意後に実装可能なモードへの切り替えを案内する。切り替え後に同じ仕様を再承認させない。
4. 既にプランモードなのにツールがない、または `/plan` が提供されていない場合は、
   確認できた制約を説明する。切り替えを繰り返し案内せず、文章形式で続けてよいかを短く聞いて待つ。
   Codex 以外で同等のUIがない場合も同様。ユーザーが文章形式を希望した場合はその希望を優先する。

切り替えはユーザー操作で行う。設定ファイルの変更や、プロンプト内の「プランモードになった」という
宣言で代用しない。モード変更だけでUI表示が必ず成功するとは保証しない。

#### 最初の質問の例

質問: **今回はどこまで作りますか？**

| 選択肢 | 説明 |
|---|---|
| まず画面を試したい | サンプルデータで画面や操作を確認します。実際の業務データの共有はまだ行いません。 |
| 実際の業務で使いたい | 複数人でデータを保存・共有し、必要に応じてログインや操作できる範囲も設定します。 |
| 画面を試してから業務用にしたい | まず画面を確認し、その結果をもとに業務用へ進める二段階です。 |

3 つ目は新たな技術構成ではなく段階的な進め方。現在のモードは `frontend-prototype` とし、
次段階の希望を仕様書へ記録する。運用版への移行は画面確認後に仕様を合意して進める。

`request_user_input_async` での例（実際の質問時だけ呼ぶ）:

```json
{
  "questions": [{
    "title": "今回はどこまで作りますか？",
    "options": [
      "まず画面を試したい — サンプルデータで画面と操作を確認します。",
      "実際の業務で使いたい — 複数人でデータを保存・共有できるようにします。",
      "画面を試してから業務用にしたい — 画面を確認してから業務用へ進めます。"
    ]
  }]
}
```

#### 続く質問も利用者の言葉で聞く

| 質問 | 選択肢の例 |
|---|---|
| 今はどのように管理していますか？ | Excelやスプレッドシート / 紙やメール / まだ決まっていない |
| 登録したデータはどう使いますか？ | 試せればよく保存不要 / 自分の端末だけに残す / チームで同じデータを使う |
| 誰が入力や変更をしますか？ | 使う人全員 / 担当者だけ、ほかは閲覧 / まだ決まっていない |

全く不明なアプリの目的を架空の選択肢に押し込めない。その場合だけ
「どんな作業を楽にしたいですか？ 例：備品の貸出、申請の受付」と短い自由入力で聞く。
「未定」が選ばれたら小さな具体例を提案する。データ保存が必要なら、その意味を説明して開発モードと整合させる。
DB、FastAPI、RBAC、D1、CORS などの技術判断は回答から開発側で行い、専門用語を理解しないと
答えられない質問にしない。資料の添付依頼はテキスト回答専用の質問ツールに入れず、通常の会話で行う。

### 着手前に提示する仕様案

- 誰が何のために使うか、アプリ名
- 主要画面と中心となる操作（例：貸出登録 → 一覧検索 → 返却）
- 入力項目、必須項目、選択肢
- 開発モード、データ保存、認証・権限の有無
- 公開先と公開範囲、今回作らない機能
- 専用プロジェクトの配置先と、残る仮定

最後に「この内容でプロジェクトを作成し、実装を始めてよいですか」と聞いて返答を待つ。
回答がなければ着手せず、修正希望があれば案を更新する。ユーザーが具体的な案に既に合意した場合は繰り返さない。

短縮モードの既定値は、選んだ開発モードで分ける。

- **フロントエンドプロトタイプ** — 一覧・検索・登録編集、サンプルデータ、共有永続化なし、Sites で動作確認
- **バックエンド込み** — ログインあり、admin・power・general、一覧・検索・登録編集、JSON ファイル保存、Cloud Run

## 開発モードを決める

新規開発では、目的と対象業務を聞く流れで Q0 も確認する。
技術用語だけで選ばせず、次の違いを短く示して推奨案を添える。

「答えやすい質問UI」の「今回はどこまで作りますか？」を使う。
フロントエンドやバックエンドという言葉だけで選択を求めない。

- 画面、項目、導線の検証が目的なら **フロントエンドプロトタイプ**を推奨する
- 複数人の共有データ、実ログイン、権限、監査、秘密鍵を使う API が必要なら **バックエンド込み**を推奨する
- ユーザーが選択済みなら質問を繰り返さず、選択と理由を復唱して仕様書へ記録する
- 「とりあえず動くものを」はプロトタイプの希望と解釈して提案するが、Q0 の確認は省かない

詳しい境界と Sites への公開方法は `references/prototype.md` を読む。

## 聞く順番

Q0〜Q2 から始め、回答に応じて Q3〜Q6 を具体化する。
開発モードと名前が決まっただけで着手しない。回答済みの内容を復唱して仕様案に反映する。

### Q0. 開発モード

`開発モードを決める`の問い方で、次のどちらかを確定する。

- `frontend-prototype` — Sites で画面・操作を確認する。共有永続化や実認証は含めない
- `backend-included` — Vue + FastAPI で、共有データ・認証・権限を含む運用可能な構成にする

### Q1. 何を管理するアプリか

> 「誰が」「何を」「何のために」使う画面か、一文で教えてください。

例:「営業担当が、顧客への貸出機材を、返却漏れを防ぐために記録する」

ここから **アプリ名（英小文字ケバブケース）** と **画面タイトル（日本語）** を決める。
自分で案を出して確認を取るほうが早い。`equipment-loan` /「備品貸出管理」のように。

### Q2. 記録する情報

> 1 件登録するときに、どんな項目を入力しますか。
> 今 Excel や紙でやっているなら、**その現物をそのまま送ってください。**
> スクリーンショットや、紙を撮った写真でも構いません。

**言葉で聞き出すより、現物を読むほうが速くて正確。**
項目名・並び・選択肢が一度に手に入り、相手も「説明する」負担が無い。
Excel・画像・PDF のどれでも読める。読み取り方は
[現物から項目表を起こす](#現物から項目表を起こす)を参照。

聞き出す単位は「エンティティ（1 件として数えられるもの）」。
主エンティティは **1〜3 個**に収める。それ以上に見えるときは、
たいてい「1 つのエンティティ ＋ その明細」か「マスタ」に分解できる。

現物が無い場合だけ、口頭で聞く。こちらから提案して確認する形にする。
「型は何ですか」と聞いても答えは返ってこない。

- 必須か、空でもよいか
- 選択肢が決まっているか（決まっているなら候補を全部出してもらう）
- 他の情報を参照するか（担当者＝ユーザー、部門＝部門マスタ）

### Q3. 一覧の見せ方

> 開いたとき、まず何の一覧が出ていてほしいですか。そこから何を探しますか。

- **一覧に出す列** — 全項目を出さない。探すのに使う列だけ（5〜7 列が上限）
- **検索・絞り込みの軸** — 「状態で絞りたい」「担当者で絞りたい」「期間で絞りたい」
- **既定の並び順** — 「新しい順」が既定。違うなら聞く
- **詳細画面が要るか** — 項目が多い、関連情報がある、履歴を見せる、のどれかなら要る

### Q4. マスタ

> 選択肢として出てくるもののうち、運用しながら増えるものはありますか。

- **ユーザー** — `webapp-auth-security` が持っている。**作らない**
- **部門・区分値** — 増えるならマスタ、固定なら enum（[判断基準](#マスタにするか-enum-にするか)）
- マスタにするものは、それ自体が一覧＋登録編集を持つ小さな CRUD になる

### Q5. 権限

> この画面を使う人を、できることで分けると何種類になりますか。

「見るだけの人」「登録もする人」「管理する人」の 3 種類に収まることが多い。
収まらないときだけ深掘りする。ここから機能キーを決める（[権限の決め方](#権限の決め方)）。
プロトタイプでは画面と導線の確認材料として扱い、サーバー側の権限判定を実装したとはみなさない。

### Q6. 運用

> 何人くらいが使いますか。データはどのくらい溜まりそうですか。

- 利用人数（同時に使う人数）
- 年間の件数 → 保存方式が決まる（[保存方式の決め方](#保存方式の決め方)）
- 社外からアクセスするか → デプロイ先とログインの要否
- 既存データの移行があるか

プロトタイプを選んでいても、ここで共有保存や実認証が必要と判明したら、
バックエンド込みへの変更を提案して Q0 の決定を更新する。

## 現物から項目表を起こす

Excel だけでなく、**画像（画面のスクリーンショット、帳票の写真）や PDF（紙の様式、
マニュアル）からでも読み取れる。** 相手が出しやすいものを出してもらうのが最優先で、
「Excel でください」と形式を指定して待つほうが遅い。

読める内容が形式ごとに違うので、**何を資料から確定でき、何を必ず聞くか**を分けて扱う。

| 資料 | 読み取る手段 |
|---|---|
| Excel / CSV | `xlsx` スキル、または `openpyxl` / `pandas` で読む。**数式ではなく値と入力規則を見る** |
| 画像（PNG / JPG） | Read ツールでそのまま渡す。画面写真・帳票の写真・ホワイトボードの写真 |
| PDF | Read ツールに `pages` を指定して渡す。文字埋め込みが無ければ `pdf` スキルで OCR する |

### 資料ごとに読めるもの・読めないもの

| 資料 | 確定できる | **必ず聞く** |
|---|---|---|
| **Excel / スプレッドシート** | 列名、実データからの型、選択肢（入力規則・実値のユニーク）、空欄の割合＝必須の目安、件数、既定の並び | 色の意味、シートをまたぐ関係、今後増える列 |
| **画像（画面のスクリーンショット）** | 項目名と並び、入力部品の種類（プルダウン／チェック／日付）、一覧の列、ボタンの名前 | **プルダウンの全候補**（閉じていると見えない）、必須の印、桁数、裏の計算 |
| **画像（紙の写真・ホワイトボード）** | 項目名、記入欄のまとまり、選択肢の並び | 手書き部分の読み違い、略語の意味、運用上のローカルルール |
| **PDF（紙の様式・帳票）** | 項目名、記入欄の大きさ＝桁の目安、□ の選択肢、注記・記入要領 | 実際に使われている項目（様式にあるが空欄運用の項目がある） |
| **PDF（マニュアル・仕様書）** | 業務の流れ、状態遷移、用語の定義 | 現状との乖離（更新されていないことが多い） |

### 読み取るときに効くこと

- **選択肢は「見えているものが全部とは限らない」。** スクリーンショットのプルダウンは
  閉じた状態で写る。実データのユニーク値も、その期間に出現したものだけ。
  **enum の候補は必ず「他にありますか」と確認する。** ここを落とすと、
  運用開始後に「選べない値がある」で止まる
- **必須かどうかは資料から確定できない。** Excel の空欄は「任意」かもしれないし
  「入れ忘れ」かもしれない。※印や赤字があってもローカルルールのことがある。必ず聞く
- **紙の様式には、システムでは要らない項目が混ざる。** 押印欄、複写用の控え番号、
  記入日、通し番号。**デジタル化で不要になるもの・自動化できるものを見分けて、
  「これは自動で入るので項目から外します」と確認する。**
  紙をそのまま写すと、使われない入力欄が並ぶ画面になる
- **Excel は 1 シートに複数のものが同居しがち。** 明細行と集計行、複数年度、
  台帳とマスタ。**そのままエンティティにしない。** 分解してから項目表にする
- **複数の資料が出てきたら突き合わせる。** 「様式」と「実際の運用ファイル」は
  だいたい食い違う。**運用中のファイルのほうが正しい**ので、そちらを優先し、
  差分は相手に確認する
- **画像は誤読する前提で扱う。** 低解像度・手書き・専門用語の略語は特に危ない。
  読み取った項目名は**そのまま項目表にして見せ、確認を取ってから**進める

### 復唱のしかた

資料から起こしたら、**仕様書の項目表の形にして相手に見せる。**
「読み取れました」で済ませない。相手が確認できるのは表の形になってからで、
文章で列挙しても目が滑る。

不明な点は空欄にせず、**こちらの推測を入れたうえで印を付ける。**
空欄だと何を答えればよいか分からないが、案が出ていれば「そこは違う」と言える。

```markdown
### 貸出記録 (loan)
```

## 項目の型

**語彙はこの 11 種類だけ。** 増やさない。
新しい型が要ると感じたら、たいてい `text` か `enum` で足りる。

| 型 | 例 | TS (`types.ts`) | Python (`domain/`) | 入力部品 | 一覧での見せ方 |
|---|---|---|---|---|---|
| `text` | 名称、備考（1 行） | `string` | `str` | `v-text-field` | そのまま |
| `longtext` | 説明、対応内容 | `string` | `str` | `v-textarea` | 先頭のみ・省略 |
| `number` | 数量、回数 | `number` | `int` | `v-text-field type="number"` | `.numeric`（右寄せ） |
| `money` | 金額 | `number` | `int` | `v-text-field type="number"` | `.numeric` ＋ 3 桁区切り |
| `date` | 貸出日、期限 | `string`（`YYYY-MM-DD`） | `str` | `v-text-field type="date"` | そのまま |
| `datetime` | 受付日時 | `string`（ISO 8601） | `str` | `v-text-field type="datetime-local"` | `YYYY/MM/DD HH:mm` |
| `bool` | 承認済み、有効 | `boolean` | `bool` | `v-checkbox` | `.chip`（はい／いいえ） |
| `enum(A,B,C)` | 状態、区分 | `'A' \| 'B' \| 'C'` | `Literal["A","B","C"]` | `v-select` | **`.chip` で色分け** |
| `ref(entity)` | 備品、案件 | `string`（id） | `str` | `v-autocomplete` | 参照先の表示名 |
| `user` | 担当者、申請者 | `string`（email） | `str` | `v-autocomplete` | 表示名 |
| `file` | 添付、写真 | `string[]`（id） | `list[str]` | `v-file-input` | 件数のみ |

**`enum` は `.chip` で色分けする。** `styles/base.css` の
`.chip--brand`（正常・完了）/ `.chip--warn`（注意・未確定）/ `.chip--danger`（異常・停止）に割り当てる。
仕様書の備考欄に「返却済=brand、貸出中=無色、延滞=danger」のように書いておくと、
実装時に迷わない（`vue-vuetify-frontend` の `references/design-tokens.md`）。

バックエンド込みでは、**検証は必ずバックエンドにも書く。** `必須` と `enum` の候補は
`domain/` 側で `ValueError` を投げる形に写す（`fastapi-backend`）。
フロントの検証は入力補助であって防御ではない。プロトタイプの入力検証は操作確認用であり、
運用上の防御として完成したものとは扱わない。

## 標準で付ける項目

**ヒアリングで聞かない。全エンティティに機械的に付ける。**

| key | 型 | 何のため |
|---|---|---|
| `id` | `text` | 主キー。UUID を採番する。連番にしない（分散書き込みで衝突する） |
| `created_at` / `created_by` | `datetime` / `user` | 「誰がいつ作ったか」 |
| `updated_at` / `updated_by` | `datetime` / `user` | 「誰がいつ変えたか」。一覧に「最終更新」として出せる |

**これを最初から入れておくのが効く。** 後から足すと、
既に入っているデータに値が無く、移行が要る。
運用に入ると必ず「これ誰が変えたの」と聞かれるので、そのときに答えられる。

レコード自体のこの 4 項目と、`webapp-auth-security` の監査ログは役割が違う。
レコード側は「いまの状態が誰のものか」、監査ログは「何が起きたかの履歴」。
**削除されたレコードについて答えられるのは監査ログだけ**なので、両方要る。

## マスタにするか enum にするか

同じ「選択肢」でも、扱いが変わる。**ここを取り違えると後で作り直しになる。**

| | enum | マスタ |
|---|---|---|
| 候補が増えるか | 増えない／増えるときはコードも変わる | 運用しながら増える |
| 誰が増やすか | 開発者 | 利用者（管理画面から） |
| 分岐に使うか | 使う（状態で処理が変わる） | 使わない（表示と絞り込みだけ） |
| 実装 | `Literal` / union 型 | JSON ファイル ＋ CRUD 画面 |
| 例 | 申請状態、優先度、区分 | 部門、拠点、取引先、備品分類 |

**判断は「利用者が画面から増やしたいか」で決まる。**
「たまに増えます」と言われたら、まずマスタにしておくほうが安全。
enum からマスタへの移行は、参照している画面を全部直すことになる。

**逆に、状態のように処理が分岐するものはマスタにしない。**
マスタにすると「新しい状態が追加されたがコードが知らない」が起こりうる。

## 権限の決め方

`webapp-auth-security` の設計に合わせ、**ロールではなく機能キーで判定する。**
ヒアリングの答えから機能キーを起こす。3〜7 個に収める。

| 相手の言葉 | 機能キー |
|---|---|
| 「見るだけの人がいます」 | `can_view` |
| 「登録・修正する人」 | `can_edit` |
| 「Excel に出したい」「メールで送る」 | `can_export` |
| 「金額は一部の人だけ」「原価は見せたくない」 | `can_view_cost` のように**データ領域で分ける** |
| 「承認する人」 | `can_approve` |
| （常に付ける） | `can_manage_users` |

**「〇〇部長だけ」のような個人・役職名が出たら、機能キーに言い換える。**
そのまま実装するとロールが増殖して破綻する（`references/rbac.md`）。

ロールは機能キーの既定値セット。既定は admin（全部）/ power（管理以外）/ general（参照のみ）。

## 保存方式の決め方

Q6 の答えから決める。**判断の根拠を仕様書に書き残すこと。**
後から「なぜファイルなのか」を再検討できる。

| 条件 | 保存方式 | デプロイ先 |
|---|---|---|
| プロトタイプで、代表データの閲覧・操作確認だけ | サンプルデータ（必要ならメモリ内状態） | Sites |
| プロトタイプで、同じ端末の再読み込み後も残したい | ブラウザ保存（端末内限定と明記） | Sites |
| 年間数千件まで、同時編集が稀 | `data/*.json` | Cloud Run |
| 追記のみで件数が伸びる（履歴・ログ） | `data/*.jsonl`（ローテート付き） | Cloud Run |
| ファイル保存のまま公開したい／常時起動／固定 IP | 同上 ＋ 永続ディスク | **`gce-cos-deploy`** |
| 同時書き込みが多い、履歴を横断検索したい | Firestore / Cloud SQL | Cloud Run |

**Cloud Run でファイル保存を選ぶときは、インスタンスを 1 に固定する。**
複数立った瞬間に書き込みが壊れる。その制約が受け入れられないなら
`gce-cos-deploy`（VM 1 台＋永続ディスク）に寄せる。

ブラウザ保存を共有データやバックアップの代わりにしない。複数人で同じデータを扱う要件が
出た時点で、仕様書の開発モードをバックエンド込みへ変更する。

## 仕様書から作るもの

仕様書の各節が、どのファイルになるか。**この対応が固定されているのが肝。**

| 仕様書の節 | 作るもの | 読むスキル |
|---|---|---|
| プロジェクト | 専用プロジェクトルート、Git、必要なら Sites 登録 | `webapp-scaffold` / `sites:sites-building` |
| 開発モード | Sites プロジェクト、または Vue + FastAPI 構成 | `webapp-scaffold` / `sites:sites-building` |
| 目的 | サイト metadata または `README.md`、画面タイトル | `sites:sites-building` / `webapp-scaffold` |
| エンティティ（プロトタイプ） | 画面用の型、代表サンプルデータ、UI 状態 | `sites:sites-building` |
| エンティティ（項目表） | `backend/domain/<entity>.py`（検証と CRUD） | `fastapi-backend` |
| 〃 | `backend/api/<entity>_api.py`（薄いルータ） | `fastapi-backend` |
| 〃 | `frontend/src/types.ts` の interface | `vue-vuetify-frontend` |
| 〃 | `composables/use<Entity>.ts`（`loading` / `error` 付き） | `vue-vuetify-frontend` |
| 画面（一覧） | `views/<Entity>ListView.vue`（`v-data-table`） | `vue-vuetify-frontend` |
| 画面（登録編集） | `components/<Entity>EditDialog.vue` | `vue-vuetify-frontend` |
| マスタ | 上と同じ一式（マスタも CRUD） | 同上 |
| 権限（プロトタイプ） | 権限別の画面・導線サンプル。実アクセス制御ではない | `sites:sites-building` |
| 権限（バックエンド込み） | `core/user_store.py` の `PermissionRecord`、`types.ts` の `Permissions` | `webapp-auth-security` |
| 〃 | 各エンドポイントの `require_permission` | `webapp-auth-security` |
| 運用（保存方式） | `data/` の形式、`config/settings.py` | `fastapi-backend` |
| 運用（Sites） | `.openai/hosting.json` と Sites 公開 | `sites:sites-building` / `sites:sites-hosting` |
| 運用（バックエンド） | `cloudbuild.yaml` / `env.yaml` または `cos.env` | `webapp-scaffold` / `gce-cos-deploy` |

**作る順番は「1 エンティティを縦に通す」。**
全エンティティの domain を作ってから api を作る、という横断の進め方をしない。
1 つ目を domain → api → types → composable → 画面まで通して見せ、
形が合っているか確認してから 2 つ目に進む。**最初の 1 つで必ず認識のズレが出る。**

## 聞き漏らしやすいこと

ヒアリングで出てこないが、後から必ず問題になるもの。
**相手は言わないので、こちらから確認する。**

| 確認すること | 確認しないと |
|---|---|
| **削除は物理か論理か** | 「間違って消した、戻せるか」に答えられない。迷ったら論理削除（`deleted` フラグ） |
| **既存データの移行があるか** | Excel の列と項目名が合わず、作り直しになる。**先に現物を見る** |
| **一意にしたい項目があるか** | 管理番号・社員番号の重複が入る。後から直すのは大仕事 |
| **一覧の既定の絞り込み** | 「終わった案件まで出て邪魔」になる。既定で「進行中のみ」が多い |
| **通知が要るか** | 「期限が来たらメールが欲しい」は後出しで来る。要るなら保存方式にも影響する |
| **同じ人が同時に開くか** | 後勝ちで上書きされる。ファイル保存なら特に |
| **Excel に出したいか** | ほぼ必ず言われる。`can_export` を最初から用意しておく |
| **いつまでに要るか** | 短縮モードで進めるかの判断材料になる |
| **資料の enum に他の候補がないか** | プルダウンは閉じた状態で写り、実データも出現した値しか含まない。運用開始後に「選べない値がある」で止まる |
| **紙の様式の項目が本当に要るか** | 押印欄・控え番号・記入日をそのまま写すと、使われない入力欄が並ぶ画面になる |

**「今はどうやっていますか」を最初に聞くと、この多くが自然に出てくる。**
現物（Excel・画面のスクリーンショット・紙の様式）を見せてもらえば、
項目・選択肢・既定の絞り込みが一度に分かる。
